# CHARGE! クリッカー制作計画

> 対象仕様: [CHARGE_CLICKER_GDD.md](CHARGE_CLICKER_GDD.md)  
> 期間: 2026-08-02〜2026-08-14  
> 方針: **面白さを小さく証明してから、コンテンツとアートを増やす**

## 1. 結論

最初から6ステージと3ボスを作らない。次の3段階を、それぞれ実際に遊べる状態で完成させる。

1. **30秒の手触り** — CHARGEとDISCHARGEだけで気持ちよいか。
2. **5分の縦切り版** — 1ステージ、アップグレード、短い敵戦でビルドの芽があるか。
3. **20分の通常ルート** — 3/6ステージ、ボス選択、通常エンディングまで一本のゲームになっているか。

この3つを通過してから真ルートを作る。30秒版が面白くなければ、ステージや素材を増やさずコアループを作り直す。

## 2. 優先順位

### Must — 提出に必須

- 6セルのCHARGE / DISCHARGE / 過充電
- 6ステージから任意の3つを選ぶ通常ルート
- 性質の異なる2ボスと選択
- 約20分の通常エンディング
- 残り3ステージ、強化ボス、真のラスボス
- セーブ、日本語・英語、マウス・キーボード・ゲームパッド・タッチ
- PixelLab製ピクセルアート、オリジナル音、明確なAI利用表記
- Webブラウザで最初から最後までクリア可能

### Should — 品質を一段上げる

- 結果画面とビルド評価
- クリア結果のコピー
- アクセシビリティ設定
- 短い実績またはチャレンジ
- ビルド別の専用演出

### Could — 時間が余れば

- Infinity Mode
- オフライン進行
- デイリーチャレンジ
- オンラインランキング
- 大量の実績や追加ストーリー

## 3. 開発フェーズ

### Phase 0 — 企画固定と計測準備（8月2日）

実施:

- GDDと制作計画をリポジトリへ保存する。
- 新作のディレクトリと最小シーンを作る。
- `GameState`、アップグレード定義、保存形式の骨格を作る。
- クリック回数、初回購入時刻、放電回数、メルトダウン回数を記録できるようにする。
- 既存3作は壊さず、ランチャーの4番目として起動できるようにする。

完了条件:

- 空のゲーム画面をWeb・デスクトップの両方で起動できる。
- 設計上の未決事項と、検証で決める事項が区別されている。

### Phase 1 — 30秒の手触りプロトタイプ（8月2〜3日）

作るもの:

- 6セル
- CHARGE入力と長押し
- 部分放電と6セル超放電
- 熱、過充電、メルトダウン
- 6〜10個の仮アップグレード
- 仮の図形、パーティクル、SE
- 最小限のAUTO

まだ作らないもの:

- ステージマップ
- ボス
- ストーリー
- 大量のPixelLab素材

品質ゲート A:

- 最初の5秒で操作が理解できる。
- 30秒以内にアップグレードを買える。
- 部分放電と満充電放電の両方を使いたくなる。
- 無音・無演出でなく、1クリックごとの反応が明確である。
- 3分触った時、次のアップグレードを試したくなる。

未達なら入力感、速度、数字、音、危険と報酬の幅を調整し、次へ進まない。

### Phase 2 — 5分の縦切り版（8月3〜5日）

作るもの:

- GENERATOR CORE 1ステージ
- 小型の敵またはミニボス
- 手動・自動・過充電の3系統が見えるアップグレード
- ステージクリアと報酬選択
- セーブと再開
- 基本HUD、設定、ゲームパッド入力
- PixelLabでリアクター1体と背景1枚のスタイル試作

品質ゲート B:

- 初見で5〜7分以内にクリアできる。
- 2回プレイすると違うアップグレードを選ぶ理由がある。
- アクティブ操作が放置より明確に速い。
- 放置型も操作量を減らす代わりに成立する。
- PixelLab素材がGodotの実寸・整数倍表示で破綻しない。

この時点で正式タイトル、基準解像度、パレット、UI密度を決定する。

### Phase 3 — 20分の通常ルート（8月5〜8日）

作るもの:

- データ駆動の6ステージ定義
- 6ステージすべてのルールと仮表示
- 任意の3ステージクリア判定
- GRID LEECHとTHERMAL TITANの通常形態
- ボス選択
- 通常エンディング、結果、スタッフロール
- 日本語・英語
- タッチ、ゲームパッド再割り当て
- 自動保存

実装順:

1. 6ステージを仮表示で遊べるようにする。
2. 全20通りの3ステージ組み合わせで進行できるようにする。
3. 2ボスを仮表示で完成させる。
4. 最後に通常エンディングと結果画面を磨く。

品質ゲート C:

- 初見プレイヤーが18〜25分で通常エンドへ到達する。
- どの3ステージを選んでも進行不能にならない。
- どちらのボスにも固有の攻略がある。
- 通常エンドでゲームを終えても不足感がない。
- Chrome、Safari、Firefoxで保存・音・入力が動く。

ここがJam提出可能な最初の完成版である。8月8日時点でこの状態を目指す。

### Phase 4 — PixelLab素材・音・演出の本統合（8月7〜10日）

Phase 2で承認したスタイルを基準に、素材をバッチ生成する。ゲーム性が確定していない機能の素材は作らない。

順序:

1. リアクターと6セル
2. ボス2体
3. 6ステージのアイコンと背景
4. 放電、熱、連鎖、クリティカルのVFX
5. 強化ボスと真ボス
6. エンディングイラストとUI装飾

各バッチで次を確認する。

- 輪郭線、パレット、光源、解像度が基準と一致する。
- Godotで整数倍表示して輪郭が滲まない。
- 当たり判定や重要UIを隠さない。
- 日本語・英語の文字幅を確保している。
- 生成元、プロンプト、手修正内容を資産台帳へ記録する。

### Phase 5 — 真ルート（8月9〜11日）

作るもの:

- 残り3ステージの強化目標
- 未撃破ボスの強化形態
- CHARGE SINGULARITY 3フェーズ
- 真エンディングと結果
- 通常エンドからの継続導線

品質ゲート D:

- リセットなしで通常エンドから自然に続けられる。
- 初見の合計プレイ時間が50〜70分に収まる。
- 真ボスが6システムすべてを使わせる。
- どのステージ選択順・主要ビルドでも撃破可能である。
- 真エンドは通常エンドとの差が十分にある。

### Phase 6 — バランス、QA、提出準備（8月11〜14日）

実施:

- 自動シミュレーションで全ステージ順と主要ビルドを走らせる。
- 初見プレイヤーの観察テストを最低5回行う。
- Chrome、Safari、Firefox、ゲームパッド、タッチを実機確認する。
- 日本語・英語の全画面を確認する。
- 音量、点滅、画面揺れ、処理負荷を調整する。
- itch.io用のカバー、スクリーンショット、説明文、操作表、AI利用表記を用意する。
- 8月14日中に提出可能版をアップロードし、最終日は不具合対応の予備日にする。

Infinity Modeは、このフェーズの必須項目がすべて完了した場合のみ追加する。

## 4. 毎日の進め方

1. その日の終了時に「ブラウザで遊べるビルド」を残す。
2. 新機能を足す前に前日のビルドを3分プレイする。
3. 1日の最重要課題を1つだけ決める。
4. 実装 → 自動テスト → 実プレイ → 数値調整の順に一周する。
5. GDDと実装が食い違った場合、意図的な変更なら決定ログへ残す。
6. 素材生成数ではなく、完成条件を通過した数で進捗を測る。

## 5. テストと計測

### 5.1 自動テスト

- 各3ステージ組み合わせから通常エンドへ到達できる。
- 4主要ビルドで両ボスを倒せる。
- 通常エンド後、正しい3ステージだけが残る。
- 強化ボスと真ボスを撃破して真エンドへ進める。
- 保存・読込後も進行、購入、言語、入力設定が維持される。
- 数値がNaN、負数、オーバーフローにならない。

### 5.2 計測するイベント

- 最初のCHARGEまでの秒数
- 最初のアップグレードまでの秒数
- 各ステージの開始・クリア・失敗時刻
- 選択したステージ順とアップグレード
- 部分放電、超放電、メルトダウンの回数
- ボス敗北理由と再挑戦回数
- 通常・真エンドの到達時間

個人情報や外部送信は不要。開発ビルドのローカルログと結果画面で確認する。

### 5.3 人間のテストで聞くこと

- 30秒後: 「何をするゲームだと思いましたか？」
- 5分後: 「今のビルドの強みは何ですか？」
- ボス解放時: 「どちらを選びたいですか。理由は？」
- 通常エンド後: 「満足して終われますか。続きを遊びたいですか？」
- 失敗後: 「次に何を変えれば勝てそうですか？」

説明してから遊んでもらわない。理解できなかった箇所をUIとゲーム内フィードバックで直す。

## 6. バランスの基準

- 価格曲線や敵HPは単一の定数群から調整できるようにする。
- ステージごとのクリア時間中央値を3〜4分へ揃える。
- 最適ビルドと弱いビルドの通常クリア時間差を、初期段階では2倍以内に抑える。
- 手動入力は同投資の自動化より高出力だが、疲労するほどの連打を要求しない。
- ボス敗北は突然の即死ではなく、数秒前から予兆と改善可能性を見せる。
- 数字の桁が増えても、短縮表記と演出で意味が読めるようにする。

## 7. 仕様変更のルール

新しい機能案は次の3条件を満たした場合だけ追加する。

1. CHARGEというテーマを強める。
2. 既存の選択やシナジーを増やす。
3. 8月14日の提出可能版を危険にしない。

該当しない案は `Post-jam` として記録し、Jam版には入れない。面白くないコアループをコンテンツ量で隠さない。

## 8. 最初に実装するチケット

1. `charge_clicker` の最小シーンとテストを追加する。
2. 6セルの状態モデルと表示を作る。
3. CHARGE / DISCHARGE / 熱 / メルトダウンを実装する。
4. クリック、満充電、放電、危険域の仮SE・VFXを入れる。
5. 10個以内の仮アップグレードをデータ定義する。
6. 初回購入時刻と各操作回数を結果表示する。
7. Webビルドで入力遅延、保存、音声開始制約を確認する。
8. 品質ゲートAを実プレイで判定する。

ここまでが次の開発単位である。ゲートAを通過した時点で、1ステージの縦切り版へ進む。

### 2026-08-02 — Phase 3キャンペーン基盤

- 6ステージの名称、固有ルール、ビルドタグ、報酬、クライマックス、目標時間を一つのカタログへ分離。
- 任意の3ステージからボス選択・通常エンドへ進み、そのまま残り3ステージ、強化ボス、CHARGE SINGULARITY、真エンドへ続く進行モデルを実装。
- Phase 2のGENERATOR COREクリア結果を、キャンペーンの1ステージ目として引き継ぐ変換を追加。
- コアループ状態とキャンペーン進行を同じ保存ファイルへ原子的に保存・復元できるよう拡張。
- ステージ選択順を変えた通常ルート・真ルート完走と保存復元を自動テストへ追加。

まだ画面へ露出していない基盤実装であり、次の単位はステージマップUIと各ステージ固有ルールのプレイアブル化。
